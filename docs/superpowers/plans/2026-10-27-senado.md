# Senado Federal no monitoramento — plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** acompanhar as proposições do Senado no mesmo radar, e-mail, planilha e painel da Câmara, com a casa sempre visível. Um projeto continua acompanhado quando muda de casa.

**Architecture:**
- A bronze do Senado fica em tabelas próprias (`bronze.sf_*`).
- A silver é compartilhada, com as colunas `casa` e `id_origem`. Cada chave do Senado recebe um deslocamento fixo (`1_000_000_000 + id`), de modo que `id_proposicao` continua sendo um único inteiro em todas as camadas, no n8n e no Power BI.
- As versões do mesmo projeto nas duas casas formam um grupo (`chave_projeto`), que propaga acompanhamento, avaliação e posição.
- Um orquestrador isola as casas: falha do Senado vira aviso e nunca derruba a Câmara.

**Tech Stack:** Python 3.14 (`requests`, `psycopg2`), PostgreSQL/Supabase, SQL views e materialized views, GitHub Actions, n8n (MCP), Power BI PBIP/TMDL.

**Spec:** `docs/superpowers/specs/2026-10-27-senado-design.md`. Leia as seções 4 e 8 antes de qualquer tarefa.

**Validação:** o Fable revisou o spec (2 rodadas) e este plano (2 rodadas, ambas "aprovado com ajustes"). Os ajustes obrigatórios das duas rodadas estão incorporados abaixo.

**Escopo deste plano:**
- As fases 0, 1 e 2 do spec estão detalhadas passo a passo.
- As fases 3 a 8 estão em nível de tarefa, com arquivos e critérios de aceite. O detalhamento delas é um plano seguinte, escrito com os números da fase 0: lista de "votado", regra de `eh_relator`, volume e mapa dos "Revisora".

## Global Constraints

- **Idioma:** código, comentários, logs, mensagens e docs em português.
- **Testes:** sem banco e sem API, tudo mockado: `.venv/bin/python -m unittest discover -s tests -v` e `.venv/bin/python -m compileall -q src tests`. Os scripts rodam de dentro de `src/`.
- **Deslocamentos:** `SENADO_OFFSET = 1_000_000_000` (processo, colegiado, parte de reunião) e `PLENARIO_SENADO_OFFSET = 2_000_000_000` (sessão do Plenário). Ficam só em `src/config.py`; no SQL, como literal comentado.
- **Casa:** `casa` é `'CD'` ou `'SF'`. Na exibição: "Câmara" / "Senado".
- **Colunas novas de view vão sempre no fim**, porque `CREATE OR REPLACE VIEW` não reordena.
- **`status_alerta`:** a regra é idêntica na gold e no api (há teste de paridade). O relógio é `now() AT TIME ZONE 'America/Sao_Paulo'`.
- **Falhas (invariantes do CLAUDE.md):** falha parcial levanta erro, faz rollback da transação abortada e não avança a janela daquela casa. `pipeline_pautas.py` nunca avança `incremental` nem `incremental_senado`.
- **Isolamento:** uma falha do Senado nunca falha o job nem bloqueia as janelas, o e-mail ou a planilha da Câmara (decisão 8.3). A transformação do Senado só escreve linhas com `id >= 1e9`.
- **Grupo:** o projeto que muda de casa é um projeto só. Acompanhamento, SIM/NÃO e posição valem para o grupo. Se houver divergência, prevalece SIM (decisões 8.1 e 8.2).
- **Escopo do Senado:** MPV vem do Senado, com a versão da Câmara no mesmo grupo. Agenda do Senado: CRA, CMA, CCJ, CAE, Plenário do Senado e as comissões mistas (CMMPV) das MPVs monitoradas, sem sessões do Congresso (decisões 8.4 e 8.5). A `casa` de uma proposição do Senado é sempre `'SF'`; `'CN'` só vale em `casa_iniciadora` e em `dim_orgao.casa`.
- **Unicidade:** `gold.vw_monitoramento` e `gold.vw_grupo_projeto` têm sempre uma linha por `id_proposicao`. Nenhum JOIN que possa multiplicar linhas. O vínculo só é lido dentro de `vw_grupo_projeto` (agregado), e o acompanhamento chega por `grupo_acompanhado`.
- **Repositório público:** nada de posições da ABCS, links de planilha, chaves ou URLs com token em código, testes ou docs.
- **n8n:**
  - `get_user_preferences` antes de alterar;
  - `validate_workflow` antes de publicar;
  - conferir as `connections` depois de cada update;
  - testes com "Enviar Alerta" desativado ou fixado. Nada de e-mail real para a Ana em teste.
- **Power BI:**
  - edição por arquivos, com o Desktop fechado (memória `pbi-edicao-por-arquivos`);
  - mockup aprovado antes de qualquer mudança visual;
  - nada de `gerar_paginas.py`.

**Interfaces — Produces:**

- `silver.tramitacao`: `casa VARCHAR(2) NOT NULL DEFAULT 'CD'` e `eh_relator BOOLEAN`.
- `silver.evento`: `casa VARCHAR(2) NOT NULL DEFAULT 'CD'`.
- `silver.evento_pauta`: `votado BOOLEAN`, `codigo_parlamentar_relator INT`, `partido_relator VARCHAR(20)` e `uf_relator VARCHAR(5)`.
- `silver.dim_orgao`: `casa VARCHAR(2) NOT NULL DEFAULT 'CD'`. O comentário no schema registra que `'CN'` vale só aqui (colegiados CMMPV) e em `proposicao.casa_iniciadora`.
- `silver.proposicao_vinculo`:
  - colunas `id_proposicao_cd BIGINT NOT NULL CHECK (id_proposicao_cd < 1000000000)`, `id_proposicao_sf BIGINT NOT NULL CHECK (id_proposicao_sf >= 1000000000)`, `origem VARCHAR(30) NOT NULL` e `data_extracao TIMESTAMP NOT NULL DEFAULT now()`;
  - PK `(id_proposicao_cd, id_proposicao_sf)`;
  - índice em `id_proposicao_sf`.

Detalhes de implementação:
- Usar `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. Num banco existente, `ADD COLUMN ... NOT NULL DEFAULT 'CD'` preenche as linhas atuais, então a CHECK vale para os dados de hoje.
- A constraint é criada dentro de `DO $$ BEGIN IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'ck_proposicao_casa') THEN ... END IF; END $$;`.
- **Backfill no fim de `schema_silver.sql`.** É idempotente, roda a cada `setup_db` e toca **só a Câmara**:

```sql
UPDATE silver.proposicao SET id_origem = id_proposicao WHERE id_origem IS NULL AND casa = 'CD';
UPDATE silver.proposicao SET data_apresentacao_origem = data_apresentacao
 WHERE data_apresentacao_origem IS NULL AND casa = 'CD';
UPDATE silver.tramitacao SET eh_relator = coalesce(descricao_tramitacao, '') ~* '^Designação de Relator'
 WHERE eh_relator IS NULL AND id_proposicao < 1000000000;
UPDATE silver.evento_pauta SET votado = (uri_votacao IS NOT NULL)
 WHERE votado IS NULL AND id_evento < 1000000000;
```

- Na transformação da Câmara:
  - `id_origem = id_proposicao` e `data_apresentacao_origem = dataApresentacao`, no INSERT e no `DO UPDATE`;
  - `tramitacao.eh_relator = coalesce(elem->>'descricaoTramitacao','') ~* '^Designação de Relator'`;
  - `evento_pauta.votado = (elem->>'uriVotacao') IS NOT NULL`.
- O `DELETE` de `evento_pauta` em `transform_eventos_to_silver.sql` ganha `AND id_evento < 1000000000`. Assim a Câmara nunca apaga pauta do Senado, e vice-versa na fase 5.

### Tarefa 1.4: Gold e api com casa, grupo do projeto e regras normalizadas

**Files:**
- Modify: `sql/schema_gold.sql`, `sql/schema_api.sql`
- Test: `tests/test_senado.py`; atualizar `tests/test_pipeline.py`

**Interfaces — Produces:**

**1. `gold.vw_grupo_projeto (id_proposicao BIGINT, chave_projeto BIGINT, ids_grupo TEXT, grupo_acompanhado BOOLEAN)`**
- Criada em `schema_gold.sql` **antes** de `vw_monitoramento`.
- Cálculo:
  - `WITH RECURSIVE` que **começa pelas arestas de `silver.proposicao_vinculo`** (não pela silver inteira);
  - percorre o grafo nos dois sentidos com `UNION` (sem `ALL`), o que garante o término em ciclos;
  - fecha com `SELECT no, min(alcancado) AS chave GROUP BY no`.
